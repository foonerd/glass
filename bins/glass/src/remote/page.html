Connection not tested

Each path to the player is tried from here. The frames path is judged from both ends: the player is asked, over the channel, to send three probe datagrams to this remote's frames port, and the verdict says whether they arrived. Where something is blocked the row names the side and the fix.

Firewall rules for this remote

A firewall on this machine (Bitdefender, Windows Defender Firewall, ufw and the like) takes a rule in these terms: the program, the direction, the protocol and the port. The ports are the player's own, as its Remotes tab sets them.

Assets

What the theme on show names, each brought here as the player offered it, failed (offered, and the fetch failed, with the reason), missing (the theme names it and the player does not have it, so the player's own screen lacks it too), or elsewhere (a path on the player, not a theme file), each with the meters that name it. The files brought are listed only with Show every file on, remembered by this browser; a report carries what is not fine, and the downloaded one every file. A file that failed is tried again at the next sync: the player's theme changing, or the remote starting again.

Prerequisites

What this machine has for the display to run: the program and how it was started, what draws the frames and whether in software, the screens, the fonts brought, and the folders the remote keeps things in.

Report

A report holds this remote's side whole, the Status, Connection, Assets and Prerequisites above with its last log lines, and the player's side as far as this remote can read it. Say in a line what you did and what you saw, then make it; it is copied for the forum, opened as a GitHub issue, or saved as a file. Addresses stay hidden unless revealed.

The Glass interface

    

      

      

    

  


  

    
Version

    

    
 

    
An upgrade fetches the release offered to this remote, checks it against the release's checksum and signature, tries it, puts it in place of the one that runs and starts the display again as it. The one before is kept beside it, as glass.prev, and comes back by itself if the new one cannot hold on. The release is looked for on the player first, where its Manager keeps archives for remotes (System tab, Install from a file), and on GitHub second; the newer of the two is offered.

    

      

      
A release is first published as a test release, tried on the project's own players, and then made the latest. With this on, as on the player's System tab, this remote is offered the newest of the repository's last ten releases, a test release among them, as soon as it is published; off, it is offered the latest release only. Applied with the other settings.

      

      
An extra for a remote that cannot reach GitHub: a release archive downloaded on another machine is installed from here, checked by the signature it carries inside, with no network. The archive is this machine's one from the release: on Linux glass-<version>-<arch>.tar.gz, on Windows the windows-x64 zip, glass-evo's for the bundle. Off, the remote refuses such uploads. Applied with the other settings.

Levels

    

      

      

      
The gain scales what the needles and bars show here. The decay is the share of its height a bar may fall per frame at most: 0.85 falls fast, 0.98 slowly, 0 (or empty) shows the bars as the player sends them. The player's own display and its audio are not touched.
